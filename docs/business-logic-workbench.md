# 业务规则与决策工作台

`/rules` 统一浏览、维护和验证匹配规则、业务约束、计算模型、决策表与决策模型。复用既有本体、谓词、模型和 ChangeSet，没有新增领域专用 source envelope。实例适用性、方案推荐和企业系统中的实际设备指派保持各自的来源与生命周期。

## 业务白板与专家模式

工作台默认进入业务模式。新建时选择要解决的问题、填写业务名称；稳定标识自动生成。普通业务人员可以使用白板、结构化表单和案例完成编制与验证，无需填写 JSON 或输入映射路径。专家模式是显示方式切换，不能代替作者、审核或发布权限。

选定逻辑后，白板占满工作区，不再保留顶部标题区和页签栏。左侧悬浮工具栏的“规则白板”按钮统一展开或收起“规则与决策”目录，不再另设目录展开按钮；工具栏还提供新建业务逻辑、创建版本或提交审核；“更多操作”中可切换专家模式并进入统一变更审核，专家模式可在此打开“定义与配置”。右上角的当前逻辑卡片显示名称、版本和状态，点击可查看业务说明或切换逻辑。右下角工具栏仅提供添加逻辑和整理视图，点击白板卡片即可打开对应的右侧属性面板；缩放工具位于左下角。“结果验证”“说明与样例”“关联与使用”“运行记录”保留在白板左侧悬浮工具栏，点击后打开居中的大弹窗，窗口内可直接切换这四项内容；标题和切换按钮固定，正文在窗口内滚动，桌面默认占屏幕高度的 88%，窄屏接近全屏，无需拖拽调整大小。可点击关闭按钮、按 Esc 或点击遮罩关闭窗口；输入和验证结果保留。白板背景、视角和缩放保持不变，卡片编制属性仍在右侧，关闭弹窗后可继续操作。目录与属性面板按需打开，节点位置不因面板切换而改变。

- 基础规则使用“输入条件 → 判断或计算 → 输出结果”白板。点击卡片打开编制面板，维护参与对象、属性、比较方式、计算组合或输出列。
- 决策表通过业务名称、值类型、比较方式和对应结果维护。支持明确的范围、集合与不限条件，以及唯一命中、首条命中和全部结果；拖动行把手或使用上下移动按钮调整顺序。
- 决策模型可从逻辑库拖入或点击添加已启用的资产。从输出圆点连接到另一步的输入圆点，会修改真实输入映射；也可以在节点编制面板通过数据来源下拉框完成同样操作。连线拒绝循环、容器类型不符、数值与是否值混接，以及未经换算的数值单位不一致。带显式单位的场景量值仍由后端作已注册的同量纲换算。
- 点击“最终结果”卡片，给业务结果命名并选择来源。已有引用会保留固定版本；本次试算完成的节点会显示完成标记。删除被引用步骤前需要先移除或调整相关连接。
- 点击“场景输入”可以维护独立的业务输入名称、值类型和单位，再在节点中选择该字段；无需手填内部字段名。自定义场景字段是决策定义中的输入说明，不是企业事实。被使用的输入需先调整连接才能删除。
- 在节点编制面板的“使用的逻辑版本”中显式升级同一逻辑的启用版本，原有映射保留供核对；接口有变化时需补齐输入并重新验证整条链。
- 拖动节点仅整理视图，不改变执行顺序；布局保留在当前页面内存中，切换资产和验证页后可恢复，不写入真源。执行顺序始终由实际输入映射决定。
- “结果验证”使用带名称与单位的业务字段、候选对象列表、预期结果表单和结果卡片。案例预期需要独立填写；数值格式按已声明的输出类型精确序列化，不用实际试算结果反向覆盖专家预期。
- 原始配置、内部标识、输入与预期 JSON、完整执行快照和来源细节只在专家模式显示。业务模式的说明与样例使用业务名称及结果卡片。

维护已登记资产仍需先“创建新版本”；界面编制只修改会话草稿。预览不写入企业事实，提交、独立审核、真源应用和验证发布继续使用原有 ChangeSet 流程。未在本轮改变决策引擎、计算方式或审核权限。

## 如何选择逻辑类型

| 类型 | 定义与要回答的问题 | 典型输入 | 主要输出 | 维护重点 |
| --- | --- | --- | --- | --- |
| 匹配规则 | 比较主体、候选及上下文的事实，判断哪些具体实例符合条件 | 主体、候选列表、具名上下文 | 合格候选集合及逐项解释 | 角色、谓词、适用范围、缺数和特例 |
| 业务约束 | 判断单个主体的事实是否满足必须成立的业务条件 | 单个主体属性 | 合法、不合法或信息不足 | 阈值、边界、现有数据影响 |
| 计算模型 | 用声明式公式执行带单位的确定性数值计算 | 变量、数值与单位 | 十进制数值、单位和过程 | 公式、量纲、精度、输入接口 |
| 决策表 | 按条件组合选择输出，并明确多行命中策略 | 场景字段或重复项字段 | 输出值、命中行、默认值使用情况 | 条件覆盖、重叠、行顺序、默认输出 |
| 决策模型 | 用无环图连接已有逻辑，组织多步骤判断和计算 | 显式场景与节点输入映射 | 具名最终结果及节点执行解释 | 固定版本、依赖、数据映射、整链案例 |

先判断要做的是数据合法性校验、实例筛选、数值计算、条件分支，还是多个步骤的组合。同一业务场景可以同时使用五类逻辑。例如“同类零件、相同工艺，但不同尺寸选用不同设备”：决策表按尺寸决定设备等级，匹配规则再按零件、工序与设备能力筛选具体设备，计算模型估算工时和能耗，决策模型连接这些步骤；业务约束检查相关事实本身是否合法。设备是否已经被实际指派，应由权威业务系统提供事实。

概念相同不意味着实例关系相同。通常优先让同一逻辑读取不同实例属性，只有明确的个别特例才使用实例 ID 范围。不同逻辑之间不存在隐含的“特例自动优先”：需要用适用条件、表的命中策略或显式决策链维护选择方式。

## 界面说明与教学样例

目录底部或白板“更多操作”中的“工作台说明与样例”可以打开五类逻辑对照，并逐类查看定义、适用场景、差异、输入输出、配置字段、维护步骤和检查重点。工具栏的“说明与样例”打开当前类型的说明面板；“规则白板”提供输入、判断与输出卡片，新建对话框提供类型摘要；试算区提供对应输入提示。

每类说明包含“用此示例新建草稿”，另建具有独立 ID 的会话草稿并打开结果验证页，保留其他草稿。用户可在“验证全部”中运行案例，并用“载入此案例试算”检查各案例输入。该操作不提交审核、不发布、不记录正式运行，也不写入企业事实。未登录或缺少作者权限时可阅读说明；示例需要的概念、谓词、单位或启用模型缺失时，界面说明缺项并禁用创建。

教学配置集中保存在 `prototype/ontology-studio/app/rules/logic-examples.json`，界面展示与自动化验证共用同一份配置。所有案例数值和 `demo:*` ID 都是虚构参数。

### 匹配规则：筛选哪些实例适用

规则用 `scope.subject_concept` 定义主体类型，用 `candidate_concept` 定义候选类型；`context_concepts` 可增加工序、工厂、订单等具名角色。输入项将变量名映射到角色和已注册谓词，条件比较输入变量与另一变量或固定值。同一概念的不同实例会因属性、上下文或适用范围不同而得到不同结果。

维护顺序：选择角色和概念 → 绑定注册谓词 → 维护主体适用条件与候选检查 → 必要时限定具体实例 → 配置符合、不符合、缺数、不同主体及上下文的案例 → 检查影响、递增版本并提交审核。输入和概念属性绑定应先在本体工作台维护；实际设备能力等事实通过其连接器维护。

教学示例比较候选功率是否满足基准设备要求，沿用已有 `equipment`、`rated_power` 和功率单位，避免凭空引入零件尺寸谓词：

```json
{
  "subject": {"rated_power": {"literal": "10", "unit": "kW"}},
  "candidates": [
    {"id": "demo:large", "rated_power": {"literal": "12000", "unit": "W"}},
    {"id": "demo:small", "rated_power": {"literal": "8", "unit": "kW"}}
  ]
}
```

比较 `available_power >= required_power`，预期 `eligible_candidate_ids = ["demo:large"]`；要求改为 6 kW 后两个候选都合格。候选缺少功率时为 `unknown`，不能认定合格。迁移为零件选型时，应先注册零件概念、尺寸和设备能力谓词及单位，再按实际角色绑定输入。

同组条件按 AND 组合。主体适用条件不成立表示不适用；候选条件不成立表示未通过；事实缺失表示信息不足。规则给出候选集合，可以是零个、一个或多个；若要求唯一推荐，需再明确排序或选择策略。`subject_ids` / `candidate_ids` 可显式限定特例，空列表表示不额外限定；缺少所需实例 ID 时返回信息不足。

### 业务约束：检查事实是否合法

业务约束要求单个主体满足所有检查条件。它与匹配规则共用属性和单位比较机制，但当前仅支持 `subject` 角色，不接受候选、上下文或实例 ID 特例范围。启用后，编译器和连接器也会执行该约束，`invalid` 或 `unknown` 都不能通过编译检查。

维护顺序：选主体概念 → 绑定主体谓词 → 填写阈值及注册单位 → 增加合法、非法、边界和缺数案例 → 评估已有实例是否满足新条件 → 递增版本并审核。修正不合法业务事实时，应回到权威来源维护。

教学示例为“设备额定功率必须大于 0 W”：输入 `{"subject":{"rated_power":{"literal":"10","unit":"kW"}}}`，预期 `results[0].verdict = "valid"`、`status = "complete"`；0 W 为 `invalid` / `blocked`；没有功率为 `unknown` / `incomplete`。

预期不合法的案例返回不合法，案例仍然通过。这说明约束正确识别了非法数据，不代表该数据可以入库。结构和引用完整性等技术约束仍由既有编译器承担。

### 计算模型：确定数值如何计算

这里的模型是有明确输入、公式、输出单位与精度的计算定义。它计算数值，条件分支和跨步骤编排分别由决策表、决策模型维护。

维护顺序：声明输入标识和单位 → 维护公式 → 设置输出单位与精度 → 增加正常值、单位换算和业务边界案例 → 检查引用工序和决策模型 → 递增版本并审核。公式支持 `input`、`const`、`add` / `sum`、`multiply`、`subtract`、`divide`、`date_diff_days`，不接受任意脚本。声明的输入必须全部被公式引用；加减、乘除和输出均需符合量纲规则。

教学示例为“工时 = 基准工时 × 工作量系数”，输入变量分别声明 `hour` 与无量纲 `one`，输出 `hour`，精度 8：

```json
{
  "inputs": {
    "baseline_time": {"literal": "1", "unit": "hour"},
    "workload_factor": "2"
  }
}
```

预期 `{"output":{"value":"2.0","unit":"hour"}}`。改成 30 minute × 2，预期 1.0 hour。纯数值输入按变量声明的单位解释；带单位对象会先换算。输出数值保留十进制字符串。维护实际价格、经验系数和汇率时还需确认事实来源；有权威汇率来源要求的模型不能通过普通手填场景绕过来源治理。

### 决策表：维护条件分支和输出

输入列包含列标识、来源 `facts` / `item`、实际字段名和 `number` / `string` / `boolean` 类型；数值列可声明注册单位。每行填写全部条件和输出，行内条件按 AND 组合。界面单元格支持 `*`、比较表达式、闭区间和集合，规范定义保存为类型化条件对象。

维护顺序：声明输入输出列 → 写规则行和边界 → 明确命中策略 → 必要时配置默认输出 → 验证边界与组合覆盖 → 发布新版本 → 显式升级工艺或决策模型引用。

| 命中策略 | 含义 | 维护要求 |
| --- | --- | --- |
| UNIQUE | 唯一规则命中 | 验证阶段拒绝重叠；未命中且无默认输出时报错 |
| FIRST | 取第一条命中规则 | 行顺序就是优先顺序；未命中且无默认输出时报错 |
| COLLECT | 收集全部命中规则 | 结果为列表；可为空列表 |

教学示例使用 UNIQUE：尺寸演示值 `<= 300` 输出 `equipment_class = small`，`> 300` 输出 `large`。输入 `{"facts":{"size":"100"}}` 预期 `{"result":{"equipment_class":"small"}}`；300 仍为 small，600 为 large。示例没有声明毫米，仅演示统一口径数值；正式尺寸规则应明确并注册长度单位，再给数值列配置单位。

表输出的设备等级可以由后续逻辑消费，不能据此认定已选择某个真实设备实例。当前是受限 DMN 式表，支持条件、命中策略与解释，尚未实现完整 DMN XML / FEEL。

### 决策模型：维护多个逻辑的依赖

决策模型使用无环图组合启用的规则、约束、公式和决策表，维护节点引用、输入映射和具名最终输出。它表达逻辑数据依赖；工艺模板表达工序编排。二者都不会因为一条依赖边而自动生成设备开工时间或产能排程。

维护顺序：先发布并启用被引用资产 → 添加固定版本节点 → 明确场景、上游节点或固定值的输入映射 → 声明最终输出 → 验证整条链及停止位置 → 发布新版本并检查引用方。发布时服务端解析并保存依赖快照，升级原始规则或公式不会静默改写已发布决策模型。

教学示例先运行 `operation_cycle_time`，再将工时传给 `operation_energy`：

```json
{
  "time_inputs": {
    "baseline_time": {"literal": "1", "unit": "hour"},
    "workload_factor": "2"
  },
  "power": {"literal": "3", "unit": "kW"}
}
```

预期最终输出为 `duration = {"value":"2.0","unit":"hour"}`、`energy = {"value":"6.0","unit":"kWh"}`。`duration` 节点将 `facts.time_inputs` 绑定至整个 `inputs` 对象；`energy` 将场景 `power` 绑定至 `effective_power`，将上游 `duration.output.value` 绑定至 `elapsed_time`。后者传递的是纯数值，必须确认上下游均为 hour，不会自动携带上游单位。

界面创建该教学草稿前检查两个启用模型的输入与输出单位接口，并使用当前可用的具体版本引用；接口不匹配时提示缺项。节点仅支持四种基础逻辑，不支持嵌套决策模型；最多 30 个节点，映射路径最多八层。约束不通过、规则信息不足或筛选后没有合格候选时，图停止并保留节点解释，最终 `output` 为空。

## 已加入真源的两个关联案例

这两个案例是已启用的教学资产，可直接在目录查看，无需先新建会话草稿。参数全部虚构，不表示企业设备能力、实际工时或生产指派。

| 案例 | 真源与固定版本 | 用途 |
| --- | --- | --- |
| 教学案例一：按尺寸选择设备等级 | `knowledge/decisions/demo_size_equipment/v1.0.0.md`；`decision:demo_size_equipment:1.0.0` | UNIQUE 表按尺寸演示值输出设备等级与无量纲工作量系数 |
| 教学案例二：尺寸选型后计算工时与能耗 | `control/decision-models/demo_size_duration_energy/v1.0.0.yaml`；`decision_model:demo_size_duration_energy@1.0.0` | 引用案例一，再调用工时、能耗公式，展示多种逻辑的协同 |

案例一配置 `size <= 300 → equipment_class = small, workload_factor = 1`，`size > 300 → large, 2`。内置 100、300、600 三个案例，300 属于 small。`size` 没有物理单位，仅是统一口径的尺寸演示数值，正式使用前应明确并注册实际单位；数值类型输出按十进制字符串显示为 `"1.0"` / `"2.0"`。

案例二的依赖是 `select → duration → energy`。`select` 接收 `facts` 并引用案例一；`duration` 接收场景 `baseline_time` 和上游表的 `workload_factor`，引用 `operation_cycle_time@1.0.0`；`energy` 接收场景 `power` 和上游 `duration.output.value`，引用 `operation_energy@1.0.0`。工时数值传递处的输入输出单位均为 hour。

| 决策链输入 | 设备等级 / 系数 | 工时 | 能耗 |
| --- | --- | --- | --- |
| size = 100；基准 1 hour；功率 3 kW | small / 1.0 | 1.0 hour | 3.0 kWh |
| size = 300；基准 1 hour；功率 3 kW | small / 1.0 | 1.0 hour | 3.0 kWh |
| size = 600；基准 1 hour；功率 3 kW | large / 2.0 | 2.0 hour | 6.0 kWh |
| size = 600；基准 30 minute；功率 3 kW | large / 2.0 | 1.0 hour | 3.0 kWh |

按以下顺序结合界面理解：

1. 刷新规则工作台目录，选择“决策表”及案例一，在“规则白板”点击判断卡片，查看条件列、输出列和命中策略。
2. 切换“结果验证”，点击“验证全部”。用各案例的“载入此案例试算”与“试算当前定义”观察命中行和输出。
3. 在案例一的“关联与使用”查看“被谁使用”，打开案例二。
4. 在案例二的“规则白板”查看三个步骤，点击卡片查看数据来源；在“结果验证”分别载入 small_part、large_part、large_half_hour，比较最终输出与节点过程。
5. 在案例二的“关联与使用”可返回被引用的表和公式。需要修改时使用“创建新版本”；内置版本保持不可覆盖。

## 通用维护与审核方式

1. 先在本体工作台确认概念、关系、谓词和单位；新增谓词先注册到 `control/predicates/`。实例属性从权威连接器采集。
2. 在规则工作台选类型、填写定义和适用范围。修改已有资产时从资产创建新版本，检查“关联与使用”中的引用方。
3. 维护专家案例。每个案例包含稳定 ID、完整输入和需要核对的非空 `expected` 对象；对象按填写字段递归比较，列表长度与顺序必须一致，十进制输出按字符串填写。
4. 运行单次试算和“验证全部”，检查错误、缺数、边界及影响。预览不写入业务事实。
5. 填写修改原因并提交 ChangeSet，由独立身份审核，再应用真源与验证发布。全部案例通过是必要条件，仍需审核业务含义及对现有数据的影响。
6. 显式升级使用方引用并再次验证。匹配规则、约束及公式递增版本后更新其当前真源；决策表和决策模型发布不可覆盖的新版本。
7. 对已发布启用资产可记录正式运行；回放核对原输入、原定义和原语义快照，场景试算结果不自动成为实际业务指派。

## 工作台协同

- 本体白板维护语义定义，可从概念、关系、谓词及规则卡片跳到关联业务逻辑；规则页面可反向定位本体定义。
- 实例详情可把主体 ID 和概念类型带入规则页面。规则支持主体、候选实体，以及最多八个具名上下文角色，例如工序、工厂、订单；各角色的概念及输入谓词都由注册定义约束。
- 工艺工作台可引用独立发布的固定版本决策表；原有随模板包发布的表继续兼容。规则页面追踪决策模型、标准工序和工艺模板的引用，模板链接可直接打开相应版本。
- 统一审核页接收全部提案，并可重新运行规则、公式、决策表和决策模型的回归案例。审核、真源应用和验证发布仍只在 `/changesets` 操作。页面链接用 `id` 定位 ChangeSet。
- 各工作台共享内存登录会话。通过应用内导航切换保留草稿；刷新页面会结束内存会话。切换登录主体会清空该规则工作台的凭证相关视图与草稿，避免跨身份误提交。

## 资产与真源

| 资产 | 真源 | 修改方式 |
| --- | --- | --- |
| 匹配规则 | `control/rules/business/<id>.yaml` | 沿用 Studio 单真源定义；递增语义版本、校验影响并审核 |
| 业务约束 | `control/constraints/business/<id>.yaml` | 同上；启用后编译器和连接器继续执行主体约束 |
| 确定性公式 | `control/models/*.yaml` | 沿用公式验证、单位检查和既有真源路径 |
| 决策表 | `knowledge/decisions/<id>/v<version>.md` | 复用规范 `decision_table` 节点与已注册的 `decision_definition` 谓词；版本不可覆盖 |
| 决策模型 | `control/decision-models/<id>/v<version>.yaml` | 通用控制定义；版本不可覆盖，使用 `knowledgeos.decision-model.v1` |

独立决策表及决策模型使用 `logic_asset` ChangeSet。所有业务逻辑提案为高风险，必须有至少一个明确预期的回归案例，且全部案例通过。应用到真源不自动创建 Git commit；未验证发布的独立资产不能被运行或其他决策、模板引用。

`test_cases` 是规范定义中的专家案例，每项包含 `id`、`input` 和非空的 `expected` 对象。预期按字段递归比较；列表要求长度、顺序和各项相符，数值结果保持后端返回的十进制字符串。用例预览和事实影响评估均不产生事实写入。

规则可以通过 `scope.subject_ids`、`scope.candidate_ids` 显式限定实例。留空表示该类型的全部实例；缺少判断所需的实例 ID 时返回信息不足。不会自动推断某条实例特例应覆盖其他规则；组合顺序和决策表命中策略须明确维护。

## 决策依赖与运行

决策模型最多包含 30 个节点，节点引用启用的规则、约束、公式或决策表。发布提案时，服务端从已发布资产解析版本并保存定义快照，客户端提供的快照不会被直接信任。之后修改原始公式或规则不会静默改变已发布决策模型。

每个节点的 `bindings` 是具名输入映射，来源只能是场景 `facts`、上游 `node` 或显式 `literal`。路径使用最多八层的字符串数组；数字字符串可访问列表项。模型使用 `inputs`，表使用 `facts` / `item`，规则使用 `subject` / `candidates` / `contexts`。`outputs` 用同样的机制声明最终输出。

编译时拒绝循环、未知节点、非法引用和无效定义；运行按依赖拓扑顺序执行。规则事实缺失、硬约束不通过或筛选后没有合格候选时，决策图停止并保留已执行节点的解释，不产生最终推荐。

实例绑定读取当前属性或指定 `as_of` 时点的已确认断言，保留来源、证据与缺项。直接绑定真实实例目前适用于规则与约束；公式及决策图使用显式输入映射的场景参数。场景参数必须与实例绑定二选一，不能混作权威事实。

正式记录只允许执行已发布、启用的资产，需 `agent` 权限及幂等键。执行结果、输入、来源、定义、谓词、本体、单位和币种快照保存在 `runtime/knowledge.state.db` 的通用 `logic_run` 表，并经事务 outbox 写入审计账本。场景运行标记为 `scenario`，真实实例评估标记为 `instance_facts`；两者都不会自动创建实际生产指派或关系事实。回放使用保存的快照，检查结果是否与原记录一致。

持久状态 schema 递增为 5，兼容恢复旧版本配对备份。state 与 ledger 仍必须一起备份；决策记录不依赖可重建的 index。

## API

| 接口 | 权限 / 行为 |
| --- | --- |
| `GET /v1/logic` | `read`；统一资产、版本、引用、语义依赖及 registry fingerprint |
| `POST /v1/logic/preview` | 普通逻辑只读预览；决策表需要既有模板作者、审核或发布权限；返回定义验证、可选试算、全部案例及来源 |
| `POST /v1/logic/propose` | 普通资产需要 `propose`，决策表需要 `template_edit`；必填 `base_revision` 与原因 |
| `POST /v1/logic/run` | `agent`；只执行已发布启用资产，幂等记录运行 |
| `GET /v1/logic/runs` | `read`；按 `ref` 或 `subject_id` 过滤后返回最近 100 次运行 |
| `POST /v1/logic/replay` | `read`；按运行 `id` 回放快照，不重新读取当前事实，不写入状态 |

既有 `/v1/business/impact` 和 `/v1/business/evaluate` 新增可选 `context_ids`，与规则工作台使用同一实例解析、单位比较及来源语义。代理只转发个人身份，不注入共享管理员凭证。

## 当前边界与本地验收

决策表沿用受限 DMN 式语义：类型化输入输出、UNIQUE / FIRST / COLLECT、范围和集合等条件。尚未实现完整 DMN XML / FEEL 互操作、任意脚本、递归决策、候选集合的通用优化求解或有限资源产能排程。

启动后端 `knowledgeos dev-serve --port 8787`，前端运行现有 `dev` 脚本并访问 `/rules`。仅该显式回环开发模式支持 `local-admin-token`；另一独立主体的 `local-reviewer-token` 可用于高风险审批测试。普通生产 `serve` 仍使用环境配置的个人凭证。

界面可从“体验不同尺寸选设备”创建虚构草稿，载入 small_part / large_part 案例试算，查看不同输出；通过应用导航切换工作台后应保留草稿。提交后进入审核页，可重新验证案例并由另一主体完成审批、应用与发布。发布的表应出现在工艺工作台的决策引用列表中。记录运行后可回放，并从运行记录返回相关主体实例。
