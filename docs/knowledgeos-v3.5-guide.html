01

需求目标：把“会回答”升级为“可依赖”

这套系统面向企业知识与 Agent，而不是把所有资料塞进一个聊天窗口。

01

统一语义

成本、行业、项目等领域共用同一个节点/判断/关系信封；领域包只调整工作流、检索、技能和工具策略。

02

可信来源

企业运营事实留在 ERP 等权威系统；人工编写知识留在 Git。每个高等级判断必须带来源与证据。

03

安全变更

Agent 的持久建议走 ChangeSet。批准不等于发布，发布必须校验真源语义结果与修订。

04

可重建运行

索引可丢弃重建；治理状态和审计账本持久保存，成对备份并校验。

图 1 · 从原始来源到可信回答的闭环实线是数据与控制路径

→
注册、校验、接入Schema · Predicate · Policy · Connector
→
统一知识投影Node · Assertion · Relation · Index
→

五维语义 C-R-L-T-P：Concept（是什么）／Relation（如何连接）／Logic（如何判断和计算）／Temporality（何时有效）／Provenance（凭什么可信）。它们是一个知识对象的不同维度，不是五套数据库。
02

架构分层：一套内核，多种入口

从上到下是用户体验、智能服务、知识 API、编译治理、持久与来源。

图 2 · V3.5 六层架构横向箭头代表不同入口共享同一内核
本地 SQLite 的状态/索引事务与账本之间通过持久 Outbox异步、幂等地衔接；不要理解成三个文件处于同一个数据库事务。当前实现面向单主机、本地文件系统，跨节点部署需另做平台适配。
03

三种“真相”与一个可重建视图

分清“内容从哪里来”和“运行时存在哪里”，就不会误把索引当主库。

Authored truth

Git 编写的知识与控制定义

knowledge/ 存经过编写/审核的知识；control/ 存本体、谓词、模型、策略、领域与技能。修改走评审与编译。

Operational truth

企业业务系统

ERP / QMS / PLM / PM 等源系统保留运营事实。连接器读取并投影，不能把这些事实反向写进 Markdown 充当真源。

Durable runtime

状态 + 审计

knowledge.state.db 管 ChangeSet、Outbox、连接器记录、模型运行和录制快照；knowledge.ledger.db 是不可随意重建的审计账本。

Disposable projection

查询索引

knowledge.index.db 用于检索、图、实体卡。它从 Git 真源与持久连接器记录重建，不单独备份为“数据真相”。

04

仓库目录：Agent 在哪里、每个文件夹做什么

“Agent”不是一个单独装着全部知识的目录，而是由通用服务、领域包、技能包与可治理的数据共同组成。

① 真源与控制面

control/跨领域规则、模型与 Agent 行为声明
knowledge/Git 编写的知识实体、研究、决策、上下文
connectors/源系统到 canonical 的映射和示例

② 执行与运行态

lib/knowledge_os/编译、API、Agent、策略、连接器等 Ruby 实现
bin/knowledgeos 命令行入口
runtime/本地 SQLite 运行数据库；不要提交 Git

③ 用户体验与验证

prototype/ontology-studio/前端 OS / 非实例控制面
tests/编译、策略、账本、API 等测试
docs/契约、Agent、抽取、迭代文档与本指南

control/ 内部：Agent 所依赖的“行为与语义地图”

ontology/概念与关系类型。core.yaml 声明组织、产品、项目等类型及有向端点、关系实体化规则。
predicates/全局判断类型注册表。每个新 predicate 先在这里注册值类型、基数、存储模式、时态/证据/权威等。
schemas/Canonical 节点、抽取源、Studio 快照等 JSON Schema；支持的 Schema 子集执行失败关闭校验。
policies/权威、新鲜度、溯源等级与维护预算。决定哪些来源可被信任，以及查询/治理中的质量状态。
models/确定性模型定义：成本汇总、进度偏差、项目风险。单位、输入和版本由程序校验。
domains/<name>/成本、行业、项目领域包：pack.yaml 管工作流/工具策略，retrieval_profile.yaml 管检索行为；不创建领域专属真源信封。
skills/<skill>/Agent 可携带技能包：SKILL.md 是人/模型可读步骤，contract.yaml 是机器可验证输入、工具白名单、模型与输出约束。
extraction/多来源抽取 profile，定义允许的来源类型与抽取策略，不负责网页抓取、语音转写本身。
constraints/跨定义完整性约束，例如 canonical integrity；属于控制面校验，而非企业业务事实。
rules/维护规则等治理规则位置；不可把规则混写到不受控的 Agent 提示词中。

knowledge/ 与实现目录

entities/实体 Markdown 或实体目录（可配外置 NDJSON assertions），使用唯一 canonical 信封与全局 ID。
research/编写型研究资料位置；必须保留源引用，不能替代运营系统中的事实。
decisions/人工形成的决策记录位置，与断言的时态、来源和审计区分。
context/编写型上下文位置，供解释与检索使用。
lib/knowledge_os/agent_service.rb 组织 Agent；compiler.rb 编译；connector.rb 接入；policy_engine.rb 治理；api.rb 提供接口。
prototype/ontology-studio/app/前端页面、知识抽取工作台、控制中心、API 代理和交互状态；属于非实例结构编辑原型。
当前仓库没有一个必须叫 Agent/ 的总目录。Agent 的可移植职责主要位于 control/skills/，执行门面位于 lib/knowledge_os/agent_service.rb，领域限制位于 control/domains/。
05

核心数据结构：一个 Node 如何承载可信知识

Canonical 信封与域无关；“稳定值”和“可争议判断”采用不同承载方式。

图 4 · Canonical Node 解剖图本图用结构示意，不代表新的字段语法
例：稳定属性
base:
  schema: { ckm: "3.0" }
  node:
    id: "org:acme"
    kind: entity
    type: organization
    key: ACME
    label: Acme Industrial Systems
knowledge:
  attrs:
    legal_name: Acme Industrial Systems Ltd.
    country: China
例：带时态与来源的判断（摘录）
knowledge:
  assertions:
    - id: assertion:acme-finding-2026-01
      predicate: finding
      value:
        type: text
        literal: ...
      temporal:
        valid_from: 2026-09-01T00:00:00Z
      epistemic:
        status: confirmed
        confidence: 0.82
      provenance:
        source_refs: [source:...]
        evidence_refs: [evidence:...]
结构代表什么典型约束不要误用为
Node ID跨领域的全局规范身份；局部业务 key 可按 namespace + type 定位不得用同名企业/项目在不同领域复制节点只靠展示名称去合并身份
attrs稳定当前属性必须使用已注册 predicate，类型正确独立有证据/争议/时态的事实
assertions可独立验证的判断predicate、值、状态、时间、溯源；Tier A 完整溯源随意写入的自由文本
relations有向节点关系端点类型、基数与实体化模式受本体约束匿名复杂合同关系的全部语义
logic_refs对逻辑/模型的引用计算结果保留模型版本、输入哈希、run ID 与 trace让模型临时心算的依据
关系何时变成节点？ 只有轻量连接用 simple edge；关系一旦需要自身 ID、属性、证据、有效期或置信度，按 reifiable / reified 规则将它作为普通知识节点建模。

控制面：定义系统能知道什么、相信什么、怎么算

新 predicate 必须先注册，才能被概念绑定、编译、查询与 Agent 使用。

图 5 · 一项事实通过控制面约束的路径示例：unit_cost（单位成本）
Predicatequantity · temporal_many · assertion
→
Ontology绑定到允许的概念；检查端点与基数
→
PoliciesERP 权威 · Tier A · 证据与时间必填
→
Value Contract显式单位、数值、引用、日期
→
Compiler / API只投影合法数据，携带质量状态

概念与关系

当前核心本体有 organization、market、product、project、task、relation、decision 等概念。关系声明有向 domain → range、端点基数和 simple/reifiable/reified 承载方式。

Predicate 与值契约

决定值是 string、text、number、quantity、enum、date、node_ref 等；量纲和货币不可暗中转换，未声明的默认单位不能猜测。

策略与模型

策略决定权威、时效、证据、写入审查和嵌入许可；成本、进度、风险运算由版本化确定性模型执行。

Embedding 默认关闭，仅在 predicate 策略允许时使用。当前本地向量是无需外部模型的确定性 hash-vector 检索；企业级 embedding provider 是扩展点，不应把它写成已接通。

08

进入知识库的两条路：Connector 与候选抽取

两条路的写入权完全不同：连接器投影运营事实，抽取只生成候选。

图 7 · 数据摄入双通道不要把抽取候选理解成入库成功
通道 A · Enterprise Connector

源记录 → Canonical 投影

源系统记录稳定业务 key / version
→
映射 + 校验注册表、Schema、权威
→
state + index持久记录与可查询投影

支持更新、错误隔离与 tombstone 删除；源引用必须保留。

通道 B · Model-neutral extraction

来源材料 → 受校验候选

文本信封正文、定位符、分段、哈希
→
模型输出当前注册表动态 Schema
→
候选校验create / update / no_change

最终结果 write_performed = false；Git 节点走 governed_changeset，运营节点回上游源系统。

网页、图片、音频、视频、邮件等可以作为来源类型；但前端需要用户粘贴已经物化的文本、OCR、字幕或转写。抓取、OCR、语音识别和企业平台导出是上游 materializer，不是这个 Studio 自动完成的事情。

指纹防过期

模型输出需回传 protocol_version 与 registry_fingerprint；本体或策略变更后，旧输出不能继续落成候选。

证据逐条匹配

Builder 会核对引用的来源分段与证据原文，未知 predicate 与不合法实体被拒绝或列为未映射事实。

权威不倒置

研究材料中的属性候选不能悄悄覆盖 ERP 等更高权威的运营值；断言仍需治理确认。

09

ChangeSet：从建议到真实发布

所有 Agent 发起的持久变更以及 Studio 定义编辑，都必须经过显式治理状态机。

图 8 · 变更状态机与关键门槛“批准”只是治理决策
proposed / review_required目标、原因、操作、base_revision 与幂等键
→
approved审核人、意见、预期语义结果
→
真源应用Git 或上游系统实际修改；编译校验
→
publishedsource revision + 预期内容验证 + 条件事务
审核亦可 rejected / changes_requested幂等 proposal / publication并发 lock_version 检查
重要：点击“批准”不会写入 knowledge/ 或 control/；填一个 Git commit 也不会自动让内容变正确。V3.5 要比较实际源文件与预期语义结果，完成编译后才登记发布。Agent 不允许直接绕过这条路径。

为什么要“预期语义结果”？

只检查源文件哈希或修订号，可能漏掉“审批的 A 变更被发布成 B 变更”。V3.5 把批准结果与发布时的真实内容绑定，降低冒名、竞态和误发布风险。

为什么要幂等与条件迁移？

网络重试与多人同时操作不可避免。idempotency_key、lock_version 和条件状态迁移避免重复创建、重复发布及覆盖别人的审核结果。

10

时间、质量、冷热层与灾后恢复

“现在是真的”与“当时系统知道什么”是两个不同的问题。

图 9 · 有效时间 vs 记录时间区间采用 UTC 明确时区、左闭右开 [from, to)
t₁ 业务发生事实自此时起有效：valid_from
t₂ 首次入库系统开始知道它：recorded snapshot
t₃ 来源更正新版本可能 supersede 旧判断
as_of 查询问 t₁ 至 t₃ 中某刻有效什么
recorded_as_of 查询问当时系统实际记录过什么

如果早期没有录制快照，系统会显式报告历史记录缺口，不倒推伪造“当时已知”的属性。

Hot

高频使用、近期或需快速响应的内容。生命周期由策略与时间判定，不代表更可信。

Warm

仍可用但访问/更新频率降低；可继续检索与追溯。

Cold

长期保留的历史或低频内容；不等于删除证据或账本。

停止所有写入者API / CLI / connector
→
离线备份两库 + 校验和 + authored fingerprint
→
匹配 Git checkout空 runtime，校验编写文件版本
→
restore → rebuild重建 index，重放连接器记录
→
verify-ledger验证哈希链与审计一致性
V3.5 的离线备份不是在线多节点高可用方案。恢复拒绝覆盖既有数据库；index.db 通过重建得到。升级前只有哈希、没有原始字节的旧连接器事件需要从上游重新接入。

登录与离线状态

Studio 使用用户个人 Bearer Token，浏览器页面内存保存，刷新后需重新登录；前端服务端代理仅转发允许的路由。未配置、未登录、权限不足和断连是不同状态。连接失败保留已有快照与草稿，但不能本地代替真实批准/发布。

演示与草稿冲突

演示模式必须主动点击进入；本地演示决策不会影响后端 ChangeSet。同步时尝试将独立编辑重基线，重叠冲突会显式显示，解决前不能提交。登录身份与 Sites/ChatGPT 托管登录是两套独立权限。

界面中的“目标契约”提示：概念属性绑定、关系端点与实体化的白板设计须由当前编译器/校验器实际接受，不能只凭画布无错就认定已在服务器发布。以服务端注册表、编译和发布验证结果为准。
